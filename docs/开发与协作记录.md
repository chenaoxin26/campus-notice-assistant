# 开发与协作记录

## 为什么做这个项目

项目发起者是学生，电脑平时留在宿舍并登录 QQ。白天可以用手机处理紧急消息，但有些通知看过后准备晚上再做，容易忘记。这个工具希望把这些通知保留下来，晚上整理成可以核对的待办。

项目发起者先了解了本地模型和界面读取等相关知识，再提出部署要求。开发中，本人负责需求、方案取舍和真实场景测试，Codex 根据要求编写代码并检查实现。

## 怎样一步步做出来

|阶段|项目发起者做了什么|Codex 做了什么|得到的结果|
|---|---|---|---|
|先试能否读取|指定测试会话，要求只读，不注入、不破解聊天数据库|检查 QQ、微信版本，尝试通过 Windows 界面接口读取文字|QQ 部分消息可以读取，微信未成功|
|尝试持续记录|要求多群测试，从手机发送消息，强调“收到消息”和“保存成功”必须分开|编写持续采集、去重和错误记录，加入指定群名单|只能读到部分界面内容，会话摘要不能代替完整消息|
|核对真实漏采|指定三个测试群，按编号发送消息并反馈结果；无法关屏的步骤明确跳过|记录各群读取情况，再测试返回电脑后的补采|最小化期间保存 2/3，同批消息返回后补采读到 3/3；关屏未验证|
|转向日常可用|要求先做好晚上补采和待办，不再无限期研究全天后台|复用已有 Ollama/Qwen，加入本地分析、任务保存和中文界面|已采集文字可以整理成任务，缺少的信息保留待确认|
|根据使用修问题|提供群聊定位失败截图，配合恢复 QQ 窗口，并追问消息超过一屏怎么办|修复重复界面节点导致的定位错误，说明历史消息读取范围|只读取 QQ 实际提供的内容，还不能自动翻页读全历史|
|增加系统通知|观察到 QQ 系统通知并提供截图，提出保留第一版，再做通知读取版本|编写 Windows 通知读取程序，检查来源，保存文字并交给模型分析|原设备上成功读到并分析过 QQ 系统通知|
|合成一个版本|要求把两版合在一起使用|统一群名单与任务列表，保留原文、完成状态和修改记录|白天监听通知，晚上主动补采，失败时可以手动补充|
|整理源码|要求完整文件包，选择 MIT 许可|去除本机路径和私有依赖，保留源码及测试，排除私人数据|默认没有任务和群名单，使用者自行设置|

## 开发中保留的判断

1. QQ 客户端收到消息、消息能被读取、程序已经保存，是三个不同状态。界面显示操作成功，也要核对正文是否真正进入数据库。
2. 相同文字可能来自不同的人，不能只按正文删除重复。通知和聊天窗口读到的相似任务也需要核对来源。
3. AI 只能分析已经得到的文字。漏采需要靠补采或手动补充；缺少的日期地点不能靠模型猜。
4. 打开群聊可能改变未读状态，补采必须由使用者主动开始。程序不绕过锁屏，不发送消息，也不读取 QQ 内部数据库。
5. 当前目标是让晚上查看任务更方便，全天和大量群聊的完整采集仍需验证。

## 已有实现

程序已实现本地模型分析、待办管理和 Excel 导出。开发设备实际使用过 `qwen3:4b-instruct-2507-q4_K_M`，约 4B 参数，采用 Q4_K_M 量化，通过本机 Ollama 调用。QQ 系统通知也有实际读取和分析记录。

这些是已有实现和小样本结果，不能保证模型每次理解正确，也不能保证所有设备、所有群的消息都能读全。

仓库不包含真实聊天和私人数据库。自动化测试使用虚构消息；历史实机结果见 [测试记录](发布验证记录.md)。

目前不支持微信自动采集：测试时无法通过 UIA 获取有效会话和消息内容，微信系统通知读取也尚未验证，只提供手动粘贴或导入。
